# 0. دستور اصلی به AI Studio

تو در این پروژه نقش یک تیم مهندسی کامل محصول را داری: معمار نرم‌افزار، مهندس ارشد Android، مهندس هوش مصنوعی و صوت، متخصص امنیت، طراح محصول و مهندس تضمین کیفیت.

هدف، ساخت یک **دستیار صوتی شخصی واقعی برای Android** است؛ نه یک دموی نمایشی، نه صرفاً یک چت‌بات با دکمه میکروفون، و نه مجموعه‌ای از قابلیت‌های ظاهری که پشت آن‌ها عملکرد واقعی وجود ندارد.

این سند مشخصات محصول، معماری، رفتار، طراحی رابط کاربری، امنیت، تست و تحویل سورس را تعیین می‌کند. تمام بندهای آن باید به‌عنوان نیازمندی پروژه بررسی و اجرا شوند.

## خروجی مورد انتظار

1. سورس کامل و قابل‌ساخت پروژه Android.
2. تمام فایل‌های لازم برای Build، تنظیمات، منابع، مجوزها و وابستگی‌ها.
3. پیاده‌سازی واقعی قابلیت‌هایی که در این سند در محدوده نسخه انتخاب‌شده قرار می‌گیرند.
4. تست‌های خودکار و گزارش تست.
5. مستندات معماری، راه‌اندازی، تنظیم APIها و Build.
6. فایل `.env.example` یا نمونه تنظیمات بدون هیچ Secret واقعی، در صورت نیاز.
7. فهرست دقیق قابلیت‌های عملیاتی، محدودیت‌های پلتفرم و مواردی که به API یا مجوز خارجی نیاز دارند.
8. راهنمای تحویل پروژه به یک Agent یا توسعه‌دهنده دیگر برای Compile، نصب و انتشار.

**مهم:** خروجی باید سورس باشد؛ نه فقط APK. قرار است سورس را به Agent توسعه خودم بدهم تا آن را بررسی، Compile، نصب و آزمایش کند.

# 1. قواعد غیرقابل‌مذاکره توسعه

- پیش از کدنویسی، ساختار پروژه، فایل‌ها، فریم‌ورک، نسخه SDK، وابستگی‌ها و معماری موجود را بررسی کن.
- اگر سورس قبلی در اختیار تو قرار گرفته، آن را مبنا قرار بده و بدون دلیل موجه بازنویسی کامل نکن.
- اگر پروژه از صفر ساخته می‌شود، ابتدا معماری و انتخاب تکنولوژی را مستند کن و سپس پیاده‌سازی را آغاز کن.
- هیچ قابلیت موجودی را بدون بررسی وابستگی‌ها حذف یا خراب نکن.
- قابلیت نمایشی، دکمه بی‌عمل، داده ساختگی، پاسخ جعلی یا Mock را به‌عنوان قابلیت نهایی تحویل نده.
- اگر سرویس خارجی، API Key، مجوز خاص یا هزینه لازم است، آن را شفاف اعلام کن؛ جایگزین جعلی نساز.
- هیچ Secret، رمز، API Key یا Token واقعی را در سورس قرار نده.
- کد باید ماژولار، قابل‌نگهداری، تست‌پذیر و دارای مدیریت خطای مشخص باشد.
- عملیات سنگین نباید روی Main Thread اجرا شوند.
- اجرای یک فرمان نباید به‌دلیل چند Listener، چند Worker یا Retry تکراری چند بار انجام شود.
- هر تغییر باید با تست Regression بررسی شود.
- هیچ قابلیت یا تستی را صرفاً برای سبزشدن گزارش، غیرفعال یا دور زده نشود.
- تا زمانی که Build، تست‌ها و بررسی‌های ضروری موفق نشده‌اند، نسخه را آماده انتشار اعلام نکن.
- اگر محدودیت Android مانع اجرای قابلیتی است، محدودیت واقعی و راهکار مجاز را توضیح بده؛ محدودیت سیستم‌عامل را دور نزن.

## روند کاری اجباری

مرحله 1: ممیزی ورودی‌ها و سورس موجود.
مرحله 2: ارائه نقشه معماری و فهرست ماژول‌ها.
مرحله 3: تعیین تکنولوژی‌ها و وابستگی‌ها با دلیل.
مرحله 4: طراحی مدل داده و قراردادهای بین ماژول‌ها.
مرحله 5: طراحی UI/UX و Design System.
مرحله 6: پیاده‌سازی مرحله‌ای هسته و قابلیت‌ها.
مرحله 7: تست واحد، یکپارچه‌سازی، UI و امنیت.
مرحله 8: رفع خطا و اجرای Regression.
مرحله 9: آماده‌سازی سورس و مستندات تحویل.
مرحله 10: گزارش نهایی با وضعیت واقعی هر قابلیت.

اگر حجم پروژه از ظرفیت یک مرحله بیشتر است، آن را به Milestoneهای مستقل تقسیم کن؛ اما در هر مرحله فایل‌ها و قراردادها را طوری بساز که مرحله بعدی بدون بازنویسی غیرضروری ادامه یابد.

# 2. تعریف محصول و تجربه موردنظر

نام محصول فعلاً قابل تنظیم باشد و نام یا لوگوی ساختگی غیرقابل‌تغییر در کد hardcode نشود.

محصول یک دستیار شخصی صوتی و متنی است که بتواند:

- فارسی معیار و فارسی محاوره‌ای ایرانی را بفهمد.
- با صدا و متن مکالمه کند.
- زمینه مکالمه را حفظ کند.
- اطلاعاتی را که کاربر اجازه ذخیره آن‌ها را داده، به خاطر بسپارد.
- درخواست‌ها را به وظایف کوچک‌تر تبدیل کند.
- با مجوز کاربر از ابزارهای مجاز Android و سرویس‌های متصل استفاده کند.
- نتیجه واقعی عملیات را بررسی کند.
- در صورت خطا، علت و راه‌حل را شفاف گزارش کند.
- در حالت Standby کم‌مصرف باشد.
- حریم خصوصی و کنترل کامل داده‌ها را در اختیار کاربر قرار دهد.

تجربه مطلوب: کاربر با دستیار صحبت می‌کند، دستیار منظور را می‌فهمد، در صورت نیاز سؤال دقیق می‌پرسد، برنامه‌ریزی می‌کند، مجوز لازم را بررسی می‌کند، عملیات را اجرا و نتیجه را راستی‌آزمایی می‌کند و سپس پاسخ صوتی یا متنی می‌دهد.

# 3. هوش زبانی و فهم فارسی

## 3.1. پشتیبانی زبانی

سیستم باید این موارد را پوشش دهد:

- فارسی معیار و محاوره‌ای ایرانی.
- جمله‌های ناقص، شکسته، دارای غلط تایپی و گفتاری.
- ترکیب فارسی و انگلیسی.
- نام اشخاص، برنامه‌ها، مکان‌ها و اصطلاحات فنی.
- اعداد فارسی و لاتین.
- تاریخ و ساعت نسبی مانند «فردا صبح»، «آخر هفته»، «دو ساعت دیگه».
- ضمیرها و ارجاع‌ها مانند «اون رو»، «همون فایل»، «بهش پیام بده».
- اصلاح درخواست در میانه مکالمه.
- درخواست‌های چندمرحله‌ای و چندبخشی.
- تشخیص تفاوت سؤال، پیشنهاد، دستور و نقل‌قول.

## 3.2. استخراج Intent و پارامترها

هر درخواست باید به ساختار مشخص تبدیل شود:

- Intent
- Entities / Parameters
- Context References
- Required Permissions
- Risk Level
- Expected Result
- Confidence
- Need for Clarification

اگر Confidence پایین است یا چند تفسیر پرریسک وجود دارد، سیستم باید قبل از اجرا سؤال کند. حدس‌زدن در عملیات حساس ممنوع است.

## 3.3. ارزیابی فارسی

یک مجموعه تست فارسی شامل درخواست‌های رسمی، محاوره‌ای، چندمرحله‌ای، دارای اصلاح، دارای ابهام و ترکیبی فارسی/انگلیسی بساز. Intent Recognition و Slot Extraction جداگانه ارزیابی شوند.

# 4. معماری صوت و مکالمه

## 4.1. زنجیره کامل پردازش

مسیر صوت باید قابل ردیابی و دارای وضعیت مشخص باشد:

Microphone Input
→ Audio Session Manager
→ Wake Word Detection
→ Voice Activity Detection
→ Speech Recognition (STT)
→ Persian Language Understanding
→ Context Resolution
→ Task Planner
→ Permission & Risk Gate
→ Action Executor
→ Result Verification
→ Text-to-Speech (TTS)
→ Return to Standby

هر مرحله باید زمان شروع، پایان، شناسه عملیات، نتیجه و خطای احتمالی را ثبت کند؛ بدون ذخیره محتوای حساس در Log.

## 4.2. مدیریت وضعیت

State Machine مرکزی با وضعیت‌های حداقل زیر پیاده‌سازی شود:

- IDLE
- STANDBY
- LISTENING_FOR_WAKE_WORD
- WAKE_CONFIRMED
- LISTENING_FOR_COMMAND
- PROCESSING_SPEECH
- UNDERSTANDING_INTENT
- PLANNING_TASK
- WAITING_FOR_PERMISSION
- EXECUTING_TASK
- VERIFYING_RESULT
- SPEAKING
- PAUSED
- ERROR
- RECOVERING

انتقال وضعیت‌ها باید معتبر و قابل‌تست باشد. هیچ Task نباید بدون وضعیت نهایی رها شود. وضعیت‌های متناقض و Listenerهای تکراری ممنوع‌اند.

## 4.3. Wake Word

- یک موتور اصلی Wake Word انتخاب شود.
- آستانه تشخیص با داده واقعی تنظیم شود، نه با حدس.
- تشخیص اشتباه در برابر صدای تلویزیون، موسیقی، گفت‌وگو و صدای خود دستیار تست شود.
- Echo Cancellation و مدیریت Audio Focus بررسی شوند.
- هر Wake Event شناسه یکتا داشته باشد.
- Listener تکراری ثبت نشود.
- پس از Wake، میکروفون به شکل صحیح به مرحله STT تحویل داده شود.
- Timeout و بازگشت به Standby درست کار کنند.
- کاربر بتواند Wake Word را غیرفعال کند و از دکمه Push-to-Talk استفاده کند.

## 4.4. تماس تلفنی: جلوگیری از بیدارشدن ناخواسته

باگ شناخته‌شده: دستیار در میانه تماس تلفنی، به‌اشتباه با صدای مکالمه بیدار می‌شود.

رفتار الزامی:

- وضعیت تماس با APIهای مجاز و سازگار Android بررسی شود.
- هنگام تماس فعال، Wake Word به‌صورت پیش‌فرض Suspend یا Mute شود.
- صدای طرف مقابل یا صدای کاربر در مکالمه به فرمان دستیار تبدیل نشود.
- هیچ Action ناشی از صدای مکالمه اجرا نشود.
- پس از پایان تماس، وضعیت تماس دوباره بررسی و سرویس صوتی فقط یک‌بار و با منابع آزادشده بازیابی شود.
- اگر تشخیص وضعیت تماس به دلیل محدودیت نسخه Android یا مجوز ممکن نبود، رفتار امن و قابل‌توضیح انتخاب شود؛ از روش‌های غیرمجاز یا دورزدن محدودیت استفاده نکن.

سناریوهای تست: تماس ورودی، زنگ، پاسخ، مکالمه طولانی، صدای مشابه Wake Word، صدای بلند طرف مقابل، پایان تماس توسط هر طرف، تماس دوم و بازگشت به Standby.

## 4.5. Voice UX

- Streaming ASR/TTS در صورت پشتیبانی Engine.
- امکان قطع صحبت دستیار توسط کاربر (Barge-in).
- جلوگیری از شنیدن صدای TTS به‌عنوان فرمان جدید.
- مدیریت Noise و Echo.
- مدیریت Audio Focus و چرخه عمر سرویس.
- اعلام وضعیت Listening / Processing / Executing.
- امکان لغو پردازش و فرمان.
- پاسخ صوتی کوتاه و طبیعی، با متن قابل مشاهده.
- در نبود اینترنت، وضعیت و قابلیت‌های آفلاین به‌صورت روشن نمایش داده شوند.

# 5. مدیریت Engineها و انتخاب موتورهای مناسب

**تعداد Engine بیشتر به معنی کیفیت بیشتر نیست. هیچ Engine جدیدی صرفاً برای افزایش تعداد قابلیت‌ها اضافه نکن.**

## 5.1. ممیزی

تمام Engineهای موجود را فهرست کن و برای هرکدام گزارش بده:

- نام و نسخه.
- وظیفه.
- محل استفاده در کد.
- Local / Native / API / Cloud.
- کیفیت واقعی فارسی.
- Streaming.
- Latency.
- RAM / CPU / Battery.
- نیاز به اینترنت و Permission.
- هزینه و محدودیت API.
- سازگاری و وابستگی‌ها.
- وضعیت نگهداری.
- خطاها و تداخل‌های شناخته‌شده.

## 5.2. معماری پیشنهادی

برای هر وظیفه یک Primary Engine انتخاب شود:

| حوزه | مسئولیت |
|---|---|
| Wake Word | یک موتور سبک و اختصاصی |
| VAD | یک موتور تشخیص فعالیت صوتی |
| STT | یک موتور تشخیص گفتار |
| NLP / LLM | موتور درک زبان و استدلال |
| Task Planner | برنامه‌ریزی وظایف |
| Action Executor | اجرای ابزارهای مجاز |
| TTS | موتور تبدیل متن به گفتار |
| Memory | سرویس مدیریت حافظه |
| Audio Session | مدیر واحد منابع صوتی |

این‌ها لزوماً نباید همگی کتابخانه‌های جدا باشند؛ هدف، جداسازی مسئولیت‌ها و جلوگیری از اجرای موازی غیرضروری است.

## 5.3. Primary و Fallback

برای هر وظیفه در صورت نیاز:

- Primary Engine
- Fallback Engine
- Health Status
- Timeout
- Retry Policy
- Circuit Breaker

Fallback فقط پس از شکست واقعی یا عدم دسترس‌پذیری Primary فعال شود. اجرای موازی بی‌دلیل، پاسخ تکراری و از دست‌رفتن Context ممنوع است.

## 5.4. Engine Manager مرکزی

یک مدیر مرکزی مسئول ثبت Engineها، انتخاب، سلامت، اولویت، منابع، Timeout، Retry، Fallback، گزارش عملکرد و آزادسازی منابع باشد.

هیچ ماژولی نباید خودسرانه Engine یا Audio Listener جدید راه‌اندازی کند.

## 5.5. Benchmark

موتورها با مجموعه ورودی یکسان مقایسه شوند: دقت فارسی، زمان پاسخ، مصرف منابع، پایداری، کیفیت صدا، عملکرد آفلاین و نرخ شکست. انتخاب نهایی با داده و گزارش مستند انجام شود.

# 6. حافظه و شخصی‌سازی

حافظه باید کنترل‌شده، قابل‌مدیریت و شفاف باشد.

انواع حافظه:

1. Short-Term: زمینه مکالمه جاری.
2. Long-Term: ترجیحات و اطلاعاتی که کاربر اجازه ذخیره آن‌ها را داده است.
3. Episodic: رویدادها و تعاملات مهم.
4. Task Memory: وضعیت وظایف در حال اجرا یا تکمیل‌شده.
5. Semantic Memory: اطلاعات و روابط مفهومی.

الزامات:

- ذخیره‌سازی با رضایت و سیاست روشن.
- ثبت منبع، زمان و میزان اطمینان اطلاعات.
- تشخیص اطلاعات متناقض و درخواست رفع ابهام.
- جلوگیری از ذخیره تکراری.
- بازیابی مرتبط، نه بارگذاری بی‌هدف تمام تاریخچه.
- جداسازی داده کاربران.
- امکان مشاهده، اصلاح و حذف حافظه.
- حذف واقعی داده از محل‌های تحت کنترل برنامه و توضیح محدودیت Backup یا سرویس ثالث.
- عدم ذخیره اطلاعات حساس غیرضروری.

# 7. برنامه‌ریزی و اجرای وظایف (Agentic Execution)

چرخه هر Task:

1. فهم درخواست.
2. استخراج هدف و پارامترها.
3. بررسی Context.
4. تقسیم کار به مراحل.
5. انتخاب Tool مجاز.
6. بررسی Permission و Risk.
7. درخواست تأیید در صورت نیاز.
8. اجرا.
9. بررسی نتیجه واقعی.
10. ثبت وضعیت.
11. گزارش نتیجه به کاربر.

هر Task دارای این فیلدها باشد:

- task_id یکتا
- created_at
- status
- steps
- selected_tool
- permission_state
- started_at / completed_at
- retry_count
- error_code
- result_summary
- cancellation_state

وضعیت‌ها: PENDING / RUNNING / WAITING_FOR_USER / COMPLETED / FAILED / CANCELLED / RECOVERING.

از Idempotency برای جلوگیری از اجرای تکراری عملیات استفاده شود. عملیات طولانی باید قابل لغو، توقف و بازیابی باشند.

## 7.1. ریسک عملیات

- کم‌ریسک: اجرای مستقیم در محدوده مجوزهای قبلاً داده‌شده.
- متوسط: نمایش خلاصه و درخواست تأیید متناسب با تنظیمات کاربر.
- پرریسک: تأیید صریح و تازه قبل از اجرا.
- غیرمجاز: رد عملیات و توضیح دلیل.

ارسال پیام، حذف فایل، اشتراک‌گذاری داده، خرید، پرداخت، تغییر امنیتی و ارسال اطلاعات به سرویس خارجی باید کنترل متناسب داشته باشند.

# 8. ابزارها و قابلیت‌های Android

قابلیت‌ها را فقط در صورت پشتیبانی واقعی دستگاه، نسخه Android، مجوز و سیاست‌های پلتفرم پیاده‌سازی کن.

ماژول‌های احتمالی:

- Contacts
- Phone / Dialer Integration
- Messaging، فقط از مسیرهای مجاز
- Notifications، با Notification Listener و رضایت روشن
- Calendar
- Files
- Media Playback
- App Launching
- Location، فقط هنگام نیاز و با رضایت
- Reminders / Alarms
- Share Sheet
- Settings Shortcuts

قوانین:

- Permission در زمان نیاز درخواست شود.
- رد مجوز باعث Crash نشود.
- از API رسمی Android استفاده شود.

- Cache و فایل موقت حساس پاک‌سازی شوند.

## 9.2. API و شبکه

- HTTPS و TLS معتبر اجباری.

- Authentication و Authorization سمت سرور.
- اعتبارسنجی Token، Expiry و Scope.
- Rate Limiting.
- جلوگیری از Replay Attack با طراحی مناسب.
- اعتبارسنجی ورودی و خروجی.
- مدیریت خطا بدون افشای جزئیات حساس.

## 9.3. Action Security Gateway

- دسترسی Tool به حداقل داده و مجوز لازم محدود شود.

- Agentها نباید به تمام ابزارها و حافظه دسترسی پیش‌فرض داشته باشند.

## 9.7. فایل و WebView

## 10.2. رفتار Delta Update

- Manifest نسخه نصب‌شده با نسخه جدید مقایسه شود.
- فایل بدون تغییر دانلود نشود.
- فایل جدید دانلود شود.
- فایل تغییرکرده فقط در محدوده مجاز به‌روزرسانی شود.
- فایل حذف‌شده فقط وقتی حذف شود که Manifest معتبر آن را حذف‌شده اعلام کرده باشد.
- دانلود مرحله‌ای و قابل ادامه طراحی شود.
- فایل ابتدا در محل موقت ذخیره و اعتبارسنجی شود.
- پس از تأیید، جایگزینی اتمیک انجام شود.
- در شکست، نسخه قبلی حفظ یا Rollback شود.

SHA-256 به‌تنهایی اصالت را اثبات نمی‌کند؛ Manifest باید از منبع قابل‌اعتماد و ترجیحاً با امضای رمزنگاری‌شده تأیید شود.

**محدودیت مهم Android:** فایل‌های Native و کد APK را نمی‌توان مانند فایل‌های عادی با جایگزینی چند فایل داخلی امن و معتبر به‌روزرسانی کرد. تغییر کد Native باید از مسیر APK امضاشده و روش نصب/به‌روزرسانی مجاز Android انجام شود. Delta Update برای Assets و منابع مستقل مناسب است، مگر اینکه سازوکار رسمی دیگری با محدودیت‌های خودش طراحی شده باشد.

UI آپدیت باید نسخه فعلی، نسخه جدید، حجم دانلود واقعی، تعداد فایل‌های تغییرکرده، پیشرفت، وضعیت و نتیجه را نمایش دهد.

تست‌ها: بدون تغییر، یک فایل تغییرکرده، فایل جدید، حذف فایل، قطع دانلود، Hash اشتباه، فضای ناکافی، شکست نصب، Crash و Rollback.

# 11. طراحی رابط کاربری: Colorful 3D Claymorphism

## 11.1. جهت هنری

رابط باید مدرن، رنگی، سه‌بعدی، دوستانه و حرفه‌ای باشد؛ با سبک **Claymorphism** و استفاده کنترل‌شده از عناصر Soft 3D.

ویژگی‌های بصری:

- کارت‌های نرم با گوشه‌های گرد و حجم سه‌بعدی.
- برجستگی و فرورفتگی کنترل‌شده (Soft Extrusion / Neumorphic Depth).
- سایه‌های چندلایه و طبیعی.
- هایلایت‌های لطیف و نورپردازی حجمی.
- گرادیان‌های زنده و رنگ‌های هماهنگ.
- آیکون‌های حجمی و یکپارچه.
- دکمه‌هایی با حس فیزیکی و بازخورد لمس.
- سطوح با عمق بصری مشخص.
- انیمیشن‌های نرم و هدفمند.
- تایپوگرافی خوانا و سلسله‌مراتب واضح.

از طراحی بیش‌ازحد شلوغ، سایه‌های سنگین، متن کم‌کنتراست، تزئینات بی‌کاربرد و افکت‌هایی که خوانایی یا عملکرد را کاهش می‌دهند پرهیز کن.

پیشنهاد جهت رنگی:

- Accent: مرجانی یا نارنجی.
- Support: زرد گرم و سبز.
- Background: زمینه روشن خنثی با سطوح رنگی لطیف.
- Dark Theme: زمینه عمیق با کارت‌های رنگی کنترل‌شده.

رنگ نهایی باید از نظر کنتراست و خوانایی بررسی شود. امکان Dark Mode و Light Mode فراهم باشد.

# 13. مدیریت خطا و بازیابی

هر ماژول باید خطاهای خود را با Error Code مشخص گزارش کند.

سناریوها:

- اینترنت قطع یا کند.
- API در دسترس نیست.
- Engine خراب یا Timeout.
- مجوز رد شده یا لغو شده.
- میکروفون در اختیار برنامه دیگری است.
- TTS یا STT شکست خورده.
- دیتابیس در دسترس نیست.
- فضای ذخیره‌سازی ناکافی است.
- عملیات Android پشتیبانی نمی‌شود.
- سرویس در Background متوقف شده.
- Process توسط سیستم Kill شده.
- Update ناقص یا نامعتبر است.

رفتار الزامی:

- Crash غیرضروری رخ ندهد.
- خطا پنهان نشود.
- Task به وضعیت نهایی برسد.
- امکان Retry فقط در صورت امن‌بودن وجود داشته باشد.
- عملیات غیرقابل‌تکرار دوباره اجرا نشود.
- پیام قابل‌فهم به کاربر نمایش داده شود.
- جزئیات فنی در Diagnostics امن ثبت شود.
- سیستم در صورت امکان به وضعیت پایدار قبلی برگردد.

# 17. معیار کیفیت طراحی و مهندسی

# 18. دستور پایانی به AI Studio

پروژه را به شکل یک محصول واقعی و قابل‌تحویل بساز.

**اولویت‌ها به ترتیب:**

1. صحت عملکرد هسته.
2. پایداری و جلوگیری از Crash.
3. امنیت و حریم خصوصی.
4. فهم دقیق فارسی.
5. عملکرد واقعی Voice Pipeline.
6. اجرای امن و قابل‌راستی‌آزمایی Taskها.
7. مدیریت صحیح Engineها.
8. تجربه کاربری ممتاز با UI رنگی، سه‌بعدی و Claymorphism.
9. عملکرد روان و مصرف منابع کنترل‌شده.
10. مستندات و قابلیت Build توسط Agent دیگر.

ظاهر زیبا جایگزین عملکرد نیست؛ همان‌طور که عملکرد فنی نیز مجوز طراحی ضعیف نیست. هر دو باید با هم تحویل شوند.

هیچ قابلیت را صرفاً با نمایش یک دکمه یا صفحه تکمیل‌شده تلقی نکن. قابلیت فقط زمانی Done است که مسیر واقعی آن پیاده‌سازی، تست و نتیجه آن تأیید شده باشد.

در پایان، سورس کامل، ساختار پوشه‌ها، مستندات Build، گزارش تست، گزارش امنیت و فهرست دقیق موارد نیازمند API یا تنظیمات خارجی را تحویل بده.

**اگر برای تکمیل پروژه اطلاعات یا سرویس خارجی لازم است، آن را دقیق مشخص کن؛ اما کار را با داده جعلی، Mock پنهان یا ادعای عملکرد غیرواقعی تحویل نده.**
